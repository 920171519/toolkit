# 架构决策记录

## 退役早期流程实现

2026-11-28，已采纳。当前工作流动作从 `lib/actions/workflow.ts` 进入 `lib/workflow.ts`。符号和入口扫描发现早期写入模块只有错误类和断言被调用，另一批早期查询和 DTO 没有可达入口。

| 方案 | 取舍 |
| --- | --- |
| 保留旧流程文件，只限制调用 | 业务类型和错误仍与整套旧状态规则耦合，读者仍需辨别两份实现。 |
| 在 Action 辅助模块中定义错误 | 领域写入会反向依赖表单或框架入口，扩大错误模块的职责。 |
| 单独保留共享业务错误并删除未调用流程 | 四个调用位置直接持有同一错误类型，流程读写各自的权威模块更明确。 |

选择第三种。`lib/domain-error.ts` 的接口只含断言和可识别的业务错误，删除这层会使错误类型和转换协议散布到写入与 Action。历史读取、启动迁移和现行 API 字段仍在使用的存储对象均保留。扩大历史数据清理范围需要当前版本和既有数据库的证据。

## 用源码依赖形成可执行约束

2026-11-28，已采纳。基线源码存在大量跨模块引用，静态解析后没有循环。使用已有 TypeScript 解析器构建图，直接接入 `pnpm lint`。图可随代码实时导出，架构文档只记录领域归属和约束。通过临时文件验证正向引用、路径别名和循环报错。

## 软件包抽屉共享授权投影

2026-11-28，已采纳。服务端首屏与 API 原先各自组装详情、编辑资格和停用阻塞项。两路改用 `getPackageDrawerData`，调用方传入用户、包和可选项目，得到完整投影或无记录。路由继续负责不同的认证响应、URL 参数和页面降级，项目工作区权限继续属于导航。把投影放在通用查询文件会混入配置阻塞项，经内部 HTTP 调用则引入请求与会话边界。共享投影让授权顺序和返回字段只维护一份。

## 隔离端到端测试资源

2026-11-28，已采纳。此前启动命令通过 POSIX shell 重置固定数据库，并沿用应用上传目录。不同测试还能独立推断数据路径。选择由 Playwright 配置生成本次运行的存储目录，`webServer.env` 为服务端设置路径，全局初始化把同一配置传给测试进程。所有直接访问 SQLite 的夹具使用同一个数据库打开入口。报告保留原数据库记录的相对路径，部署可选配置实际存放目录。

按平台维护两套命令会让行为继续分化。新增启动器可在 Playwright 退出后自动删除临时数据，同时增加信号转发和 UI 生命周期管理。目前由系统临时目录保留测试数据用于排查，避免在 Windows 的测试服务还持有文件时执行清理。并行运行使用独立检出及不同端口，UI 模式重启后获得新演示库。

## 共享转正资格和阻塞证据

2026-11-28，已采纳。原先发布服务和引导视图分别判断版本及项目状态、未结束批次、待审批电子流和绑定完成情况。把 UI 引导用于写入会把权限、链接和文案带进事务。抽取纯布尔条件会让两个调用方继续分别拼装证据。选用 `trial-readiness` 提供转正检查，集中读取有效证据和计算阻塞原因，写入在已有授权检查之后调用，引导按各项目读权限展示证据。

进入待转正的既有规则维持原状。待审批电子流可能在节点确认后补交，允许版本留在待转正队列，实际发布时再校验。数据若出现待转正与绑定方式待决定并存的矛盾状态，发布和引导都按绑定方式待定处理。现行状态转换不会产生该组合，历史迁移仍保留。

## 节点确认共用条码统计

2026-11-28，已采纳。节点详情、工作台、转正引导与提交服务使用 `binding-barcode-results` 计算同一套统计和确认门槛。已审批的 PASS 按条码原值去重，已审批的待判定记录及有效电子流里的 FAIL 按记录计数。确认失败原因、业务权限与状态仍由提交事务校验。工作台在同一 SQLite 查询读取授权待办与条码证据，受限详情对可见电子流重新统计。

继续分别维护 SQL 计数和页面判断会让重复条码和补交电子流产生分歧。选择从共同证据计算，并保留已确认节点及免绑记录供转正校验。对门槛为零或负数的异常历史记录，工作台和引导也采用提交规则的最低 1 个已审批 PASS。

## Linux 回归和 Shell 换行

2026-11-28，已采纳。Windows 检出在 `core.autocrlf=true` 时曾把部署脚本转换为 CRLF，Bash 语法检查失败。仓库为 `.sh` 固定 LF，Windows 导出也保持脚本字节一致。Linux 回归使用独立临时检出、锁定依赖和浏览器，测试数据归入该次运行的临时目录。

## 注册账号与会话写入的事务边界

2026-11-28，已采纳。旧注册 Action 先提交账号，再写会话。会话写入失败时数据库会留下账号，原表单无法用该工号重试。认证服务现在在同一 SQLite 事务中创建账号和会话，工号冲突由现有唯一约束处理。登录与注册共用会话写入，登录持久化时继续校验已验证的密码哈希。事务成功后设置 HTTP Cookie，表单负责就地提示和重试。
